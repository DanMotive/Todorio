# Аудит безопасности: что исправлено

Все правки сделаны без изменения существующих контрактов API и поведения фронтенда:
старые запросы, старые ссылки и старые сессии продолжают работать. Схема БД расширяется
только аддитивно (`migrations/0012_security.sql`).

## Сессии

- **Лимит сессий на пользователя.** `limits.login.max_sessions_per_user` раньше по умолчанию был `0`,
  то есть безлимит: утекший пароль давал любое число параллельных входов, и старые сессии
  никогда не вытеснялись. Дефолт — `10`. Семантика `0 = без лимита` сохранена (ТЗ, раздел 10),
  явно выставленное админом значение не трогается.
- **Скользящее продление** (`last_used_at`): активная сессия не выкидывает на 30-й день, брошенная
  истекает по графику. Запись не чаще раза в 5 минут.
- **Смена пароля завершает чужие сессии** (текущая сохраняется) — раньше угнанная сессия переживала
  смену пароля.
- **`Secure` на cookie за reverse-proxy**: учитывается `X-Forwarded-Proto`. `SameSite=Lax` оставлен специально:
  `Strict` сломал бы переходы по ссылкам из Telegram-уведомлений.

## Аутентификация и 2FA

- **TOTP-реплей**: принятый код запоминается (`totp_last_counter`) и больше не работает оставшуюся
  минуту с половиной. Окно ±1×30с и формат кода не изменились.
- **Повторный setup больше не гасит рабочую 2FA**: новый секрет живёт в `totp_pending_secret` и
  промоутится только после подтверждения кодом, в одной транзакции.
- **Коды восстановления** (10 шт., одноразовые): потеря телефона больше не означает потерю
  аккаунта. Вводятся в то же поле, что и код из приложения. Показываются в карточке 2FA один раз.
- **Поаккаунтная блокировка подбора кода** (5 ошибок → 15 минут): пространство кодов всего 10⁶,
  а по-IP лимит обходится сменой адресов.
- **Тайминг-оракул на логине**: для несуществующего пользователя теперь тратится то же время, что и на
  проверку хеша, иначе по задержке можно было перебирать логины.
- **Регистронезависимые логины**: `Admin` больше нельзя зарегистрировать рядом с `admin` и выдавать себя
  за него в упоминаниях и комментариях. Если такая пара уже есть — миграция не падает, а пишет
  предупреждение.
- **Гонка при регистрации** разведена: дубль логина — 409, реальная ошибка БД — 500 с записью в лог.
- **Автовыдача root первому зарегистрировавшемуся** закрывается настройкой
  `policy.registration.bootstrap_root` (по умолчанию `true` — поведение не меняется).

## Rate limiting

- **Гонка в счётчике попыток** закрыта: проверка и инкремент теперь под одним локом
  (`begin`/`end`), параллельный залп больше не проскакивает лимит.
- **Подмена IP через `X-Forwarded-For`**: заголовок читается справа налево и только от доверенных
  (loopback/private) адресов — раньше любой клиент обнулял свой лимит одним заголовком.
- **Утечка памяти лимитера**: записи протухают и выметаются каждые 5 минут.
- **Пароль публичной ссылки** больше не подбирается бесконечно (`limits.share.max_attempts`, 10).
- **Ограничение параллельных argon2id-хешей** (4): без него сотня одновременных логинов
  запрашивала ~6.4 ГБ памяти.

## Права доступа

- **Глобальная роль `viewer` теперь потолок**, а не пожелание: членство в списке или пространстве
  больше не даёт такому аккаунту прав на запись (`listPermission`, `spaceRole`).
- **`policy.sharing.public_links` проверяется при чтении**, а не только при создании ссылки:
  выключение шаринга раньше не закрывало уже выданные ссылки.

## Транспорт и заголовки

- **CSRF**: меняющие состояние запросы проверяются на same-origin (`Sec-Fetch-Site` → `Origin` →
  `Referer`). Токен не вводился, чтобы не трогать фронтенд. GET/HEAD/OPTIONS не затронуты, так что
  SSE и публичные страницы работают как раньше.
  *Побочный эффект:* скриптам и curl для записи теперь нужен `-H "Origin: <адрес>"`.
- **CSP** со `script-src 'self'` — проверено, что в `web/index.html` нет inline-скриптов и внешних
  источников, так что сборка укладывается в политику как есть.
- **Таймауты HTTP-сервера** (`ReadHeaderTimeout`, `IdleTimeout`) — защита от Slowloris.
  `WriteTimeout` и `ReadTimeout` сознательно не выставлены: первый оборвал бы SSE-поток
  `/api/events`, второй — длинную загрузку вложения на слабом канале.

## Совместимость

- Новый эндпоинт `POST /api/public/{token}` с паролем в теле запроса. Старый
  `GET /api/public/{token}?password=` работает без изменений.
- `POST /api/me/totp/enable` дополнительно возвращает `recovery_codes`; старые клиенты поле просто
  игнорируют.
- Сигнатуры `auth.DestroySession` и `auth.DeleteOtherSessions` расширены — это внутренний пакет,
  внешних потребителей нет.
- Новые строки локализации добавлены в `en-US` и `ru-RU`; остальные локали штатно падают на `en-US`.

## Не сделано сознательно

- Пароль при `/api/me/totp/setup` и `/disable` — сломало бы текущий UI (`extras.tsx`).
- `SameSite=Strict` — сломало бы вход по ссылкам из Telegram.
- Отдельное поле trusted-proxy в конфиге — заменено эвристикой loopback/private, чтобы не требовать
  редактирования `config.json` при обновлении.

## Важно перед деплоем

В песочнице не было ни Go, ни сети, поэтому `go build`, `go vet` и `go test` не запускались.
Сигнатуры, импорты и вызовы сверены вручную, но перед пушем прогоните локально:

```sh
gofmt -l ./cmd ./internal
go build ./... && go vet ./... && go test ./...
npm --prefix web run build
```

# Второй этап: устойчивость

## Лимит размера тела запроса

`readJSON` читал тело целиком. Любой авторизованный пользователь мог отправить на `/api/tasks`
гигабайтный JSON и выесть память процесса — сервер падал раньше, чем успевал ответить 400.
Теперь тело ограничено `maxJSONBody = 1 MiB` через `io.LimitReader`, плюс включён
`DisallowUnknownFields`: опечатка в имени поля больше не проходит молча как «поле не задано».

Загрузки файлов это не затрагивает — они идут через multipart и свой лимит
`limits.uploads.max_file_size_mb`.

## Метаданные и «бомбы» в загрузках

- **EXIF/GPS.** Фотография с телефона несёт координаты съёмки и модель устройства. Поставив её
  аватаркой, пользователь публиковал домашний адрес всем в спейсе. Новый `internal/api/imagemeta.go`
  вырезает EXIF/XMP/IPTC/комментарии из JPEG, текстовые чанки и `eXIf` из PNG, чанки `EXIF`/`XMP `
  из WebP. ICC-профиль, JFIF-заголовок и `iCCP` сохраняются — они влияют на отображение, а не на
  приватность. GIF не трогается: его расширения несут управление анимацией.
- **Декомпрессионные бомбы.** PNG 40000×40000 весит несколько килобайт и разворачивается в 6.4 ГБ.
  Размер холста читается из заголовка до любого декодирования; потолок — `maxImagePixels`
  (50 мегапикселей).
- **Квота считалась по заявленному размеру.** `checkStorageQuota` доверял `header.Size` из
  multipart-заголовка, то есть числу, которое присылает клиент. Теперь квота повторно проверяется
  по фактически записанным байтам.
- **У аватарок не было лимита частоты.** `/api/me/avatar` не вызывал `enforceAction`, в отличие от
  вложений. Добавлены `enforceAction` и `countAction` по тому же счётчику `uploads_per_hour`.

Файлы больше `maxInMemoryImage` (32 МБ) идут на диск потоком без очистки, как и раньше: держать
такое в памяти — обменять одну проблему на другую.

## Graceful shutdown и логи

- По `SIGINT`/`SIGTERM` сервер перестаёт принимать новые соединения и даёт текущим запросам 10
  секунд (`shutdownGrace`) на завершение. Раньше `systemctl restart` рвал соединения посреди
  записи в БД. Второй сигнал завершает процесс немедленно.
- SSE-поток `/api/events` живёт бесконечно и в отведённые 10 секунд не уложится — это ожидаемо:
  `EventSource` в браузере переподключается сам.
- `log/slog` с текстовым handler'ом в stderr. Стандартный `log` перенаправлен в него же, поэтому
  существующие вызовы в 44 файлах переписывать не пришлось — формат journald не меняется.
- Отдельный `/healthz` не добавлялся: `GET /api/health` уже есть и отдаёт версию.

## Тесты

Без БД, только чистые функции — запускаются на голом `go test ./...`:

| Файл | Что проверяет |
| --- | --- |
| `internal/auth/totp_test.go` | реплей кода, окно ±1 шага, мусор на входе, `TOTPURL` |
| `internal/auth/recovery_test.go` | формат `abcde-fghij`, алфавит без `il01o`, нормализация, хеш |

| `internal/api/ratelimit_test.go` | учёт in-flight попыток, гонки под `-race`, sweep, `clientIP` |

# Третий этап: поиск, аудит-лог, динамические подписи

Миграция: `migrations/0013_search_audit.sql`. **Требует PostgreSQL 12+** — используются генерируемые
колонки (`GENERATED ALWAYS AS ... STORED`).

## 1. Полнотекстовый поиск

**Было.** `/api/search` делал три запроса вида `title ILIKE '%текст%'`. Лидирующий `%` делает
индекс принципиально неприменимым: каждый поиск — три последовательных скана целиком, и сортировка
только по дате — точное совпадение в заголовке могло оказаться ниже случайного упоминания в описании.

**Стало.** В `tasks`, `notes`, `comments` добавлены генерируемые колонки `search_tsv` и GIN-индексы к ним.
Генерируемые — а не триггеры — чтобы индекс физически не мог разойтись с текстом. Сортировка теперь по
`ts_rank`, дата — вторичный критерий.

Конфигурация — `simple` (без стемминга). В проекте 13 языков, одна таблица на всех, а чужой стеммер хуже
отсутствия стеммера. Компенсация — префиксный поиск: каждое слово запроса получает `:*`, поэтому
«задач» находит «задачи».

**Фолбэк сохранён.** Если полнотекстовый проход вернул ноль строк, выполняются старые `ILIKE`-запросы
без изменений. Это закрывает три случая, где FTS объективно слабее: совпадение в середине слова, языки без
пробелов (китайский, японский) и запрос из одной пунктуации. Итог: поиск стал быстрее, но не стал уже.

`searchTSQuery` санитизирует ввод: всё, кроме букв и цифр, становится разделителем. Это одновременно режет
фразу на слова и вырезает символы, которые `to_tsquery` считает синтаксисом (`& | ! <-> ( )`): без этого
поиск по «`a & b`» возвращал бы 500. Максимум 10 терминов.

## 2. Аудит-лог админских действий

До сих пор одобрение пользователя, выдача роли admin, блокировка, сброс пароля, необратимое удаление
задач/списков/пространств и смена серверных настроек не оставляли следа. При двух админах на вопрос
«кто заблокировал аккаунт» ответа не было.

Таблица `admin_audit` + `internal/api/audit.go`. Запись ведётся в 8 точках:
`user.approve`, `user.status`, `user.reset_password`, `task.delete_permanent`, `list.delete_permanent`,
`space.delete_permanent`, `setting.change`, `locale.toggle`.

Два правила:

- **Сбой лога не ломает действие.** Админ, блокирующий нарушителя, не должен получить ошибку из-за
  недоступности таблицы — неудача уходит в лог приложения.
- **Секреты не пишутся никогда.** Сброс пароля фиксирует только факт, без временного пароля;
  `telegram.bot_token` записывается как `(redacted)`.

`actor_username` хранится снимком, чтобы след пережил переименование или удаление аккаунта.
Чтение: `GET /api/admin/audit?limit=&actor=&action=` (для админов). Фронтенд не тронут — это новый
эндпоинт, а не изменение старого.

## 3. Динамические подписи

**Найденная проблема.** Миграция 0010 загружает 728 фраз: 7 категорий × 13 языков. Код выбирал только
четыре категории. `perfect_day`, `inactive` и `project` — 312 фраз, переведённых на 13 языков, — не могли
появиться никогда.

Причина: старый свитч знал только два числа — сколько сделано и сколько просрочено. Фразы вроде
«Nothing left behind» говорят о третьем — сколько осталось открыто, а этого числа у функции не было.

**Стало.** Добавлен один дешёвый запрос на число открытых задач в пространстве, и чистая функция
`captionCategory(done, overdue, open)` с порядком:

| Категория | Когда |
| --- | --- |
| `overdue` | просрочено больше, чем сделано |
| `perfect_day` | есть сделанное, нет просроченного и доска пуста |
| `inactive` | ничего не сделано и ничего не просрочено |
| `success` | ≥ 10 задач, работа ещё есть |
| `project` | ≥ 3 задач и сделано не меньше, чем осталось |
| `focus` | ≥ 3 задач, но бэклог перевешивает |
| `neutral` | 1–2 задачи |

`perfect_day` требует именно пустой доски, потому что ровно это утверждают сами фразы.

**Подпись больше не бывает пустой.** `pickCaption` идёт по цепочке: язык пользователя → `en-US` той же
категории → `neutral`. Раньше отсутствующая строка давала молча пустую подпись.

Формат ответа `caption{part1, part2, category}` не изменён, фронтенд править не нужно.

## Тесты этапа

| Файл | Что проверяет |
| --- | --- |
| `internal/api/search_test.go` | санитайзинг `searchTSQuery`: все операторы tsquery вырезаются, кириллица, пустой ввод, лимит терминов, отсутствие висячих `&` |
| `internal/api/stats_test.go` | правила `captionCategory`; достижимость всех 7 категорий; похвальная подпись никогда не сочетается с просрочкой |

Тест `TestCaptionCategoryAllCategoriesReachable` — защита от повторения исходной ошибки: он упадёт,
если правка порогов снова сделает какую-то категорию недостижимой.

## Важно перед деплоем

- Миграция 0013 добавляет генерируемые колонки, а `ALTER TABLE ... ADD COLUMN ... GENERATED ... STORED`
  переписывает таблицу целиком под блокировкой. На большой базе — одноразовая пауза при старте.
  Раннер выполняет каждую миграцию в транзакции, поэтому `CREATE INDEX CONCURRENTLY` здесь неприменим.
- Код не собирался и не тестировался: в среде, где он писался, нет Go. Обязательно прогнать
  `gofmt -l ./cmd ./internal`, `go build ./...`, `go vet ./...`, `go test ./... -race`.

# Четвёртый этап: функциональные доработки

Этот этап не про безопасность, а про пять функций, выбранных из списка идей. Общее правило то же:
существующая логика и фронтенд не ломаются, все новые эндпоинты добавляются рядом со старыми.

## 1. Уведомление о разблокировке

`tasks.blocked_by` живёт в схеме с миграции 0002 и рисуется на таймлайне, но на него никто не
реагировал: когда блокирующая задача наконец закрывалась, ждущий узнавал об этом случайно. Данные
были, а обещание, которое они дают пользователю, не выполнялось.

Новый файл `internal/api/unblock.go`:

- `findUnblocked` ищет задачи, у которых закрытая задача была в `blocked_by` и **не осталось других
  незакрытых блокеров**. Уведомлять на каждую закрытую зависимость по отдельности было бы шумом:
  человеку важен момент, когда работать действительно можно.
- Висячий id (блокер удалён) считается выполненным условием - иначе задача осталась бы заблокированной
  навсегда, без возможности это заметить.
- Уведомление `task_unblocked` уходит исполнителю (если он не сам закрыл блокер) и наблюдателям,
  плюс системная запись в ленте задачи и событие `task.updated` в SSE.
- Вызов добавлен в `handleUpdateTask` только на переходе в `done` (`*in.Status != oldStatus`), чтобы
  повторное сохранение уже закрытой задачи не слало уведомления заново.

Строки `notif.kind.task_unblocked` и `task.system.unblocked` добавлены во все 15 локалей. Без этого
`trServer` вернул бы голый ключ прямо в Telegram.

## 2. Нагрузка на команду

`GET /api/spaces/{id}/workload?days=7` - `internal/api/workload.go`.

`weight` до сих пор использовался только задним числом, в статистике: сколько сделано. Вопрос, который
на самом деле задаёт владелец пространства перед раздачей задач - кто перегружен, а у кого пусто -
ответа не имел. Тот же вес, посчитанный вперёд: открытые задачи, просроченные, попадающие в ближайшие
N дней, и отдельно заблокированные (они в очереди, но работать над ними нельзя - смешивать их с
остальными значило бы показывать человека занятым, когда он на самом деле стоит).

- Строка с `assignee_id IS NULL` возвращается отдельным полем `unassigned`: работа, которую никто не
  взял, - ровно то, что такой вид обязан показывать.
- Приватные списки не протекают: то же условие видимости, что в задачах и поиске. Сводка не должна
  становиться боковым каналом к спискам, которые вызывающий не может открыть.
- Смотреть может любой участник пространства: это те же данные, что он и так видит в списках, только
  просуммированные, а вид «кто перегружен» под замком у владельца теряет смысл.
- `even_share` - справочная линия (общий вес / число людей), не цель.

## 3. Импорт CSV и Trello

`POST /api/import/csv?name=...`, `POST /api/import/trello?name=...` - `internal/api/import_external.go`.

Старый `/api/spaces/import` понимал только собственный экспорт, то есть был путём миграции ниоткуда.
Оба новых формата **не получили своей вставки в базу**: они переводятся в тот же документ `spaceExport`
и передаются существующему импортёру через клон запроса. Именно в нём лежит транзакция, ремап
parent/child, разрешение имён в пользователей и проверка права создавать пространства; вторая копия
всего этого неизбежно разошлась бы с оригиналом.

- CSV: заголовки сопоставляются свободно (`Due date`, `due_at`, `DEADLINE` - одно и то же), даты
  читаются в семи форматах, нечитаемая дата отбрасывается, а не роняет весь файл. Исполнитель
  передаётся именем и разрешается импортёром - неизвестное имя оставит задачу без исполнителя, но
  никогда не повесит её на похожего по логину человека.
- Trello: списки → списки, карточки → задачи, пункты чек-листов → подзадачи своей карточки.
  Архивные списки и карточки пропускаются - это чужая корзина. Метки сохраняются строкой в описании,
  потому что своего аналога у них пока нет, а молча терять их нельзя.
- Готовым считается только `dueComplete`: карточка в колонке «Done» - всё ещё просто карточка в
  колонке, и угадывание по названию ошибалось бы примерно в половине случаев.
- Лимиты: 8 МБ на CSV, 32 МБ на Trello, 5000 строк на запрос.

## 4. Заметки → задачи

`POST /api/notes/{id}/tasks`, `GET /api/notes/{id}/tasks` - `internal/api/notes_tasks.go`,
колонка `tasks.source_note_id` (миграция 0014).

`parseNoteTaskLines` берёт из Markdown только **невыполненные** чекбоксы. Отмеченный пункт - работа,
которую автор уже считает сделанной, и открытая задача из него была бы прямой ошибкой. Обычные буллеты
тоже игнорируются: в заметке они чаще контекст, чем обязательство, а функция, превращающая каждый
буллет в задачу, даёт список, который никому не нужен.

Связь односторонняя и слабая: правка заметки не трогает задачи, удаление заметки их не удаляет
(`ON DELETE SET NULL`). Заметка - запись разговора, задача - принятое обязательство; синхронизация
означала бы, что одно молча переписывает другое.

Список-получатель обязан быть в том же пространстве и требует прав `editor` - иначе доступ к заметке
стал бы способом писать в любой список по угаданному id.

## 5. Личный Telegram-бот

`POST /api/me/telegram/bot`, `POST /api/me/telegram/bot/confirm`, `DELETE /api/me/telegram/bot` -
`internal/api/telegram_personal.go`, `telegram.WaitForStart`, колонки `users.telegram_bot_token` и
`users.telegram_bot_username`.

Раньше Telegram работал, только если root вставил токен в настройки сервера: одно решение за всех.
Теперь любой пользователь приносит свой токен от @BotFather и получает уведомления через своего бота,
без серверной настройки вообще. Если есть оба токена, побеждает личный - он выбран самим адресатом.

**Почему у личных ботов нет постоянного опроса.** Каждый токен - отдельный бот со своей очередью
обновлений, в общий цикл `Run()` он не встраивается. Горутина на каждого пользователя означала бы
долгоживущее соединение на каждый аккаунт, который когда-либо пробовал функцию, - навсегда и ради
ничего. Слушать бота нужно ровно один раз, в момент привязки: дальше доставка исходящая. Поэтому
`confirm` слушает конкретного бота до 30 секунд и ловит `/start <код>`; отправленный заранее `/start`
подхватывается из очереди, потому что опрос начинается с offset 0.

- Токен проверяется через `getMe` до сохранения - опечатку видно сразу, а не через сутки молчания.
- Смена токена сбрасывает `telegram_chat_id`: этот чат принадлежал прошлому боту.
- Токен **никогда** не возвращается в браузер (наружу идёт только публичный @username бота), не пишется
  в аудит и не попадает в экспорт. Хранится он в открытом виде, как и глобальный: в приложении нет
  управления ключами, которым его можно было бы зашифровать, не перенеся ту же проблему на другой
  секрет на том же диске. Это осознанный компромисс, а не недосмотр.
