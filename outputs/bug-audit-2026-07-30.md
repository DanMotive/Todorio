# Todorio — аудит багов

Дата аудита: 30 июля 2026

## Резюме

Read-only аудит выявил **12 существенных дефектов** и несколько системных зон риска. Наивысший приоритет имеют ошибки начальной регистрации и администрирования: при конкурентной регистрации возможно появление нескольких root-пользователей, одноразовые приглашения можно погасить несколько раз, а обычный admin может сбросить пароль другому admin или root.

Frontend production-сборка проходит. Go-тесты в текущей среде не удалось запустить, поскольку бинарник `go` отсутствует.

## Приоритет исправлений

1. Закрыть захват привилегий: root bootstrap, reset-password, роли approval.
2. Сделать регистрацию по invite атомарной.
3. Устранить ложный успех в административных и пользовательских мутациях.
4. Сделать многошаговые изменения транзакционными.
5. Починить password-protected public links и актуализировать старый AdminPage.
6. Добавить обработку ошибок и диагностические состояния во frontend.

## Критические и высокие

### BUG-01 — конкурентная первая регистрация может создать несколько root

**Серьёзность:** Critical  
**Уверенность:** высокая; подтверждено статическим анализом

**Код:**
- `internal/api/auth_handlers.go:81-107`
- `migrations/0001_init.sql:4-24`

**Причина:** обработчик отдельно выполняет `SELECT count(*) FROM users`, затем отдельно `INSERT`. Два параллельных запроса могут оба увидеть `total == 0` и оба выбрать `role='root'`. В схеме нет ограничения, допускающего только одного root.

**Воспроизведение:** на пустой БД одновременно отправить два валидных `POST /api/register` с разными username.

**Влияние:** получение максимальных прав более чем одним пользователем; возможен захват нового публично доступного экземпляра.

**Рекомендация:** выполнять bootstrap в транзакции с сериализацией или advisory lock. Дополнительно добавить частичный уникальный индекс на root-роль, например уникальность константного выражения `WHERE role='root'`, и корректно обрабатывать конфликт.

### BUG-02 — одноразовый invite можно использовать несколько раз

**Серьёзность:** High  
**Уверенность:** высокая; подтверждено статическим анализом

**Код:**
- `internal/api/invites.go:23-47`
- `internal/api/auth_handlers.go:49-61, 103-129`
- `migrations/0003_invites_shares.sql:5-13`

**Причина:** `lookupInvite` проверяет `used_count < max_uses`, пользователь вставляется, и только после этого `consumeInvite` отдельным best-effort запросом увеличивает счётчик. Проверка и потребление не атомарны; `used_count` также не ограничен CHECK-условием относительно `max_uses`.

**Воспроизведение:** параллельно зарегистрировать двух пользователей с одним invite, у которого `max_uses=1`.

**Влияние:** обход ограничения числа регистраций, особенно опасный при `invite_only`.

**Рекомендация:** объединить создание пользователя и погашение invite в одной транзакции. Атомарно выполнять `UPDATE invites SET used_count=used_count+1 WHERE id=$1 AND used_count < max_uses AND ... RETURNING role`; отсутствие строки считать использованным/истёкшим приглашением.

### BUG-03 — обычный admin может сбросить пароль root или другого admin

**Серьёзность:** High  
**Уверенность:** высокая; подтверждено маршрутом и проверкой ролей

**Код:**
- `internal/api/admin_users.go:134-162`
- `internal/api/api.go:417-427`
- `internal/auth/session.go:37`

**Причина:** `handleResetPassword` требует только `requireAdmin`; целевая роль не загружается и не сравнивается с ролью инициатора. `IsAdmin()` возвращает true и для root, и для admin.

**Воспроизведение:** войти как обычный admin и вызвать `POST /api/admin/users/{root_id}/reset-password`.

**Влияние:** полный захват root-аккаунта и сервера.

**Рекомендация:** запретить reset root через web; разрешить управление admin-аккаунтами только root. Запретить сброс собственного root-пароля этим административным endpoint или потребовать отдельное подтверждение/повторную аутентификацию.

### BUG-04 — reset-password возвращает временный пароль, даже если пароль не изменён

**Серьёзность:** High  
**Уверенность:** высокая

**Код:** `internal/api/admin_users.go:145-161`

**Причина:** ошибки `UPDATE users` и `DELETE FROM sessions` игнорируются, `RowsAffected` не проверяется.

**Воспроизведение:** вызвать endpoint с несуществующим id или смоделировать сбой БД при UPDATE.

**Влияние:** интерфейс показывает бесполезный временный пароль и пишет audit-событие об операции, которой не было. При частичном сбое старые сессии могут остаться активными.

**Рекомендация:** выполнить update и удаление сессий в транзакции; проверить ошибку и `RowsAffected()==1`; только после commit возвращать пароль и писать audit.

---

### BUG-05 — approve допускает произвольную роль и выполняет side effects без обновления пользователя

**Серьёзность:** High  
**Уверенность:** высокая

**Код:** `internal/api/admin_users.go:42-84`

**Причина:** роль проверяется только на особые значения `admin` и `root`; значения вроде `garbage` не отклоняются. После `UPDATE ... WHERE status='pending'` не проверяется `RowsAffected`. Для несуществующего или уже обработанного пользователя всё равно выполняются notification, `postApprove`, audit и возвращается `{ok:true}`.

**Воспроизведение:** отправить approval с `role:'garbage'`; повторно approve уже активного пользователя; approve несуществующий id.

**Влияние:** повреждённые роли, дублирование onboarding-данных, ложный audit и ложный успех.

**Рекомендация:** allowlist `user|viewer|admin`; проверить `RowsAffected`; выполнять изменение статуса и обязательные side effects транзакционно либо сделать `postApprove` строго идемпотентным.

### BUG-06 — устаревший AdminPage обращается к несуществующим маршрутам и неверному DTO

**Серьёзность:** High для админ-панели  
**Уверенность:** высокая; контракт подтверждён регистрацией маршрутов

**Frontend:** `web/src/viewsPageC.tsx:491-579`  
**Backend routes:** `internal/api/api.go:56-61, 234-242`

**Несовпадения:**
- UI: `GET /api/admin/invites`; backend: `GET /api/invites`.
- UI: `POST /api/admin/invites`; backend: `POST /api/invites`.
- UI: `PATCH /api/admin/users/{id}`; такого маршрута нет.
- UI: `PATCH /api/admin/settings` с целым объектом; backend ожидает `POST /api/admin/settings` с `{key,value}`.
- UI проверяет `u.approved`, но backend возвращает `status`.
- UI предлагает роль `member`, backend использует `user`.

Все ошибки запросов подавляются через `.catch(() => {})`, поэтому панель выглядит пустой или неработающей без объяснения.

**Рекомендация:** удалить/заменить legacy AdminPage либо привести его к текущим endpoint и DTO. Добавить типы вместо `any` и показывать ошибку загрузки/сохранения.

## Средний приоритет

### BUG-07 — password-protected public link нельзя открыть через UI

**Серьёзность:** Medium  
**Уверенность:** подтверждено frontend/backend контрактом

**Код:**
- `web/src/extras.tsx:399-443`
- `web/src/sharing.tsx` — создание ссылки с password
- `internal/api/shares.go:130-193`

**Причина:** frontend всегда выполняет только `GET /api/public/{token}` без password. Backend корректно возвращает 401 `password required` и поддерживает безопасный `POST /api/public/{token} {password}`, но формы ввода пароля в `PublicListPage` нет.

**Влияние:** пользователь может создать защищённую ссылку, которая фактически не открывается штатным интерфейсом.

**Рекомендация:** при 401 показывать форму пароля и повторять запрос методом POST; отдельно обрабатывать 429, 404 и 410; не использовать query-параметр пароля в новом UI.

---

### BUG-08 — повреждённый localStorage темы может уронить приложение до входа

**Серьёзность:** Medium  
**Уверенность:** высокая

**Код:** `web/src/App.tsx:123-131`

**Причина:** `JSON.parse(localStorage.getItem('todorio.theme'))` выполняется при render без try/catch и без проверки структуры.

**Воспроизведение:** установить `localStorage['todorio.theme']='{'` и перезагрузить страницу.

**Влияние:** белый экран/падение всего React-дерева; пользователь не может войти и самостоятельно исправить настройку через UI.

**Рекомендация:** безопасный parse с fallback, проверка `color` и `visual` по allowlist, удаление повреждённого значения.

---

### BUG-09 — frontend массово показывает ложный успех после failed API mutation

**Серьёзность:** Medium; High для отдельных административных действий  
**Уверенность:** подтверждено во многих обработчиках

**Примеры:**
- `web/src/extras.tsx:459-468`: note помечается сохранённой или модалка закрывается после failed PATCH/DELETE.
- `web/src/viewsPageC.tsx:171-186`: форма filter очищается и локальное состояние меняется после failed POST/DELETE.
- `web/src/viewsPageC.tsx:260-267`: bulk archive игнорирует ошибки каждого DELETE.
- `web/src/viewsPageC.tsx:461-469`: read notification подавляет ошибку.
- `web/src/App.tsx:223-227, 342-346`: локальные theme/sound расходятся с server profile после failed PATCH.

В TSX найдено около **101** точного вызова `.catch(() => {})`; не каждый из них является багом, но значительная часть стоит на мутациях.

**Влияние:** потеря доверия к интерфейсу, риск закрыть страницу с несохранёнными данными, скрытая частичная обработка bulk-операций.

**Рекомендация:** единый mutation helper/state (`idle|saving|success|error`), отображение `ApiError`, обновление локального состояния только после успеха, rollback для optimistic UI, сводка частичных ошибок для bulk-операций.

### BUG-10 — счётчик unread растёт, пока открыта страница уведомлений

**Серьёзность:** Medium  
**Уверенность:** высокая

**Код:** `web/src/App.tsx:172-190`

**Причина:** effect обнуляет unread только при изменении `view` на `notifications`. Каждый SSE event затем безусловно делает `setUnread(n => n + 1)`, даже когда пользователь уже находится на этой странице.

**Влияние:** badge показывает непрочитанное уведомление, которое пользователь уже видит; список также не подписан на автоматический reload по SSE.

**Рекомендация:** хранить актуальный view в ref и не увеличивать badge на открытой странице; передавать событие странице для prepend/reload; либо периодически сверять count с сервером.

---

### BUG-11 — backend подтверждает запись/прочтение notification после ошибки БД

**Серьёзность:** Medium  
**Уверенность:** высокая

**Код:**
- `internal/api/api.go:465-510`
- `internal/api/social.go:353-368`

**Причина:** ошибки INSERT/UPDATE notification игнорируются. `notify` может отправить SSE и Telegram после failed INSERT. Read endpoint всегда отвечает `{ok:true}` после failed UPDATE.

**Влияние:** пользователь получает live push, но уведомление отсутствует в истории; прочитанное снова появляется непрочитанным; диагностики серверной проблемы нет.

**Рекомендация:** проверять и логировать все ошибки записи. Публиковать SSE/Telegram только после успешной persistence. Read endpoint должен возвращать 500 при failed UPDATE.

---

### BUG-12 — применение шаблона может оставить частично созданный список и вернуть успех

**Серьёзность:** Medium  
**Уверенность:** высокая

**Код:** `internal/api/templates.go:207-234`

**Причина:** список, membership и tasks создаются без транзакции; ошибки membership/tasks игнорируются. После успешной вставки списка функция всегда возвращает listID.

**Влияние:** пустой/частичный список, отсутствие owner membership, потерянные задачи при DB constraint/error.

**Рекомендация:** транзакция с rollback на любой ошибке; обязательная проверка каждого Exec; commit только после полного применения шаблона.

## Дополнительные подтверждённые риски

### Каскадное удаление доступа неатомарно

`internal/api/members.go:124-167` и `244-278`: membership удаляется, затем отдельными запросами удаляются list grants и снимаются assignee; ошибки последних запросов игнорируются. Возможен частичный revoke: пользователь уже удалён из space, но сохранил list access или остался назначенным. Нужна транзакция.

### Изменение статуса пользователя неатомарно

`internal/api/admin_users.go:89-131`: status, удаление sessions и снятие assignee выполняются отдельно, ошибки игнорируются. Endpoint может вернуть успех после частичной операции. Нужна транзакция и обработка ошибок.

### `readJSON` принимает trailing JSON/мусор

`internal/api/api.go:288-294`: выполняется только один `Decode`, EOF после объекта не проверяется. Тело вроде `{"status":"active"}{"extra":1}` может быть принято как первый объект. Рекомендуется второй Decode и требование `io.EOF`.

### Сервер молча пропускает повреждённую locale

`internal/api/notif_text.go`: ошибки чтения/JSON locale приводят к silent continue. После недавнего повреждения locale это способно вернуть English/raw key без server log. Нужен warning с именем locale и startup integrity check.

## Сборка и тесты

### Frontend

Команда:

```text
npm --prefix web run build
```

Результат: **успешно** (`tsc -b && vite build`).

Артефакт JS:

```text
dist/assets/index-DT6neZfv.js 704.09 kB; gzip 222.30 kB
```

Vite предупреждает о chunk больше 500 kB. Это не runtime-баг, но увеличивает initial load. Рекомендуются route/component-level dynamic imports и `manualChunks`.

### Backend

Команда `go test ./...` не была выполнена: в среде отсутствует `go` (`go: command not found`). Поэтому backend-выводы основаны на статическом анализе; race-сценарии необходимо закрепить интеграционными тестами с PostgreSQL.

### Автоматизированные проверки, которых не хватает

1. Параллельная регистрация двух первых пользователей — ровно один root.
2. Параллельное погашение invite `max_uses=1` — ровно один успешный account.
3. Матрица admin/root authorization для status/reset/approve.
4. Rollback template application при ошибке N-й task.
5. Public share password flow UI test.
6. Frontend test на malformed `todorio.theme`.
7. Contract test AdminPage ↔ зарегистрированные API routes.

## Отличие багов от улучшений

Не классифицированы как непосредственные дефекты:

- JS chunk 704 kB — производительность/архитектура.
- Browser notification click только фокусирует окно — UX-улучшение, пока переход к task явно не обещан.
- SSE bus сбрасывает события медленным подписчикам — допустимая стратегия, если есть периодическая сверка.
- Старый GET public share с password в query — совместимость; новый UI должен использовать POST.
- Серверное DND по `time.Now()` — потенциальная timezone-проблема, но требуется подтвердить модель пользовательских часовых поясов.
